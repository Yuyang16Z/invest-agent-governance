# 投资 Agent 回答质量与个性化治理平台

持续评测、定位并改善投资 Agent 的回答质量：每条回答经过「数字抽取 → 扶摇数据核验 → 规则与 LLM 评审 → 根因归因 → 人工复核路由」，按版本对比并过发布闸门；同时明确哪些事实不能因用户画像而改变。

## 1. 目标用户

| 用户 | 在平台上做什么 |
|---|---|
| 投资 Agent 的产品经理 | 看各意图、各维度的合格率；决定候选版本能不能上线（发布闸门） |
| 算法 / Prompt 工程师 | 看版本对比和退化样本，知道问题出在路由、数据、Prompt 还是模型 |
| 数据工程师 | 看“数据时效”“数据缺失/接口失败”类根因和接口异常记录 |
| 合规 / 风控 | 看红线命中原文、适当性、隐私复述；确认高危项 |
| 人工复核员 | 只处理被路由进来的回答，逐维度“同意 / 推翻”，推翻结果用于校准规则 |

## 2. 核心设计

### 2.1 不同问答意图的质量标准与可计算指标

六类意图（行情、财务、基金、公告资讯、热点、个性化建议）各有时效要求、是否必须风险提示、不变事实与允许的个性化范围，定义在 [`src/core/standards.ts`](src/core/standards.ts)，网页“质量标准”页直接渲染这份配置，文档与实现不会分叉。

题目列出的五类问题对应六个质量维度（隐私单列），共 22 项检查：

| 维度 | 对应问题 | 代表性检查与口径 |
|---|---|---|
| 相关性 | 答非所问 | 槽位覆盖（标的/指标/时间）、LLM 评审 0/1/2 分、热点漂移、不当拒答 |
| 数值准确 | 数字错误 | 每个数字按**声明精度**与扶摇数据比对（写到一位小数就允许最后一位差 1；“约/超过/不到”按区间） |
| 时效 | 时效过期 | 数字若等于更早交易日/报告期的数据，判为“旧数据当最新”而不是“数字错”；时点标注；热点 24h / 资讯 7 天窗口 |
| 个性化 | 个性化失真 | 适当性（C 级 vs R 级）、测评过期处理、**画像不变性**（同题多画像事实一致、不选择性遗漏） |
| 合规 | 合规越界 | 收益承诺、确定性预测、直接买卖指令、风险揭示、传闻、绝对化、诱导杠杆；否定/引述/假设语境不计 |
| 隐私 | 隐私边界 | 回答复述 L2 精确值或 L3 信息；Agent 上下文是否超出最小化范围（看 trace） |

每个指标都带分子、分母、口径和不达标样本 ID，见 [`src/core/metrics.ts`](src/core/metrics.ts)。

### 2.2 自动评测、数据核验、人工复核、用户行为反馈的分工

| 环节 | 覆盖 | 负责 | 不负责 | 衔接 |
|---|---|---|---|---|
| 自动评测·规则 | 100%，入库即跑 | 红线、风险揭示、时点标注、槽位、适当性、隐私 | 语义层面的“答没答到点子上” | 高危命中一律送人工确认 |
| 自动评测·LLM | 100%，离线批量 | 相关性 0/1/2、个性化贴合、疑似因画像改口 | 数字对错、合规定性 | 与规则冲突或置信度 < 0.7 送人工 |
| 数据核验·扶摇 | 所有识别出指标的数字 | 数值对错、是否旧数据、跨画像是否一致 | 定性判断 | 接口失败/数据缺失/找不到出处 → “无法核验”送人工，**不默认通过** |
| 人工复核 | 路由子集 | 高危确认、无法核验、评审分歧、负反馈但评测通过、5% 哈希校准抽样 | 全量逐条看 | 推翻率校准阈值，确认的 Bad Case 进回归集 |
| 用户行为反馈 | 线上全量弱信号 | 发现漏检（改写重问、点踩、追问来源），按流量排优先级 | **不作为质量真值，不参与闸门**（用户可能更喜欢“稳赚”式回答） | “负反馈但评测通过”送人工 |

### 2.3 模型 / Prompt / 数据版本对比与 Bad Case 归因

被测 Agent 由六个组件组成：模型、Prompt、数据版本、热点策略、KYC 注入策略、路由。相邻版本尽量只改一个组件，这样指标变化可以直接归因；多因素变更时，页面会明确提示“只能整体归因”。

| 版本 | 模型 | Prompt | 数据 | 热点 | KYC | 说明 |
|---|---|---|---|---|---|---|
| V1 线上基线 | deepseek-flash | P1 基础版 | D1 行情缓存 T-5 | H1 不过滤 | K1 原样注入 | 起点 |
| V2 | 同上 | **P2 治理版** | D1 | H1 | K1 | 只换 Prompt |
| V3（线上） | 同上 | P2 | **D2 最新** | **H2 相关性+24h** | **K2 最小化** | 数据与上下文治理（多因素） |
| V4 候选 | **deepseek-v4-pro** | P2 | D2 | H2 | K2 | 只换模型 |
| V5 候选 | deepseek-flash | **P3 亲和力版** | D2 | H2 | K2 | 只换 Prompt |

对比使用同一评测集的**配对检验**：McNemar 精确检验 + 配对 bootstrap 95% 置信区间（固定种子，可复现）。

单条 Bad Case 的归因看 trace：路由意图与标注不符 → 路由；数字等于 Agent 上下文里的旧值 → 数据时效；上下文是对的、回答写错 → 模型生成；Prompt 没写这条要求 → Prompt；KYC 原样注入导致复述 → KYC 注入。每条归因都附证据，复核员可以推翻。

发布闸门（[`src/core/compare.ts`](src/core/compare.ts)）：红线不多于基线且 ≤ 2%、隐私复述 = 0、适当性 = 100%、画像不变性 = 100% 为硬性规则；数值准确率、时效、槽位覆盖为软性规则；高危命中未经人工确认时为“待确认”。

### 2.4 KYC、热点上下文、合规与隐私边界

- **KYC 字段分级**：L1（风险等级、测评状态、经验、期限、目标、持仓代码）可用于个性化；L2（精确资产、收入、持仓市值、精确年龄、城市）只以分档进入上下文、回答不得复述；L3（姓名、手机号、证件号、银行卡号）隔离存储，任何版本的 Agent 都拿不到。问题文本入库前统一脱敏。
- **热点上下文**：H1 把热榜前 8 注入每个问题（基线做法），会把回答带偏、并把旧热点当今日热点；H2 只在热点类问题或与标的相关时注入，并限定 24 小时。
- **合规**：规则带编号、命中原文和豁免原因（否定 / 引述 / 假设语境）。适当性规则：Cn 只能推荐 R1–Rn；测评过期不得推荐产品。
- **不能因用户画像而改变的事实**：行情与估值及其时点；财务数据及口径；基金净值、收益、回撤、经理；产品风险等级；负面与风险信息；必要的风险揭示（只能加强）；对未来的不确定性；适当性规则本身。允许变的是表达深度、信息排序、在适当性内选择的产品类别、风险提示的强度（只增不减）。由 `PER-INVARIANT` 检查保证：同一问题让 2–4 个画像分别提问，逐项比对。

## 3. 本次评测结果（可追溯）

5 个版本 × 32 条评测项 = 160 条真实生成的回答（DeepSeek），事实快照取自扶摇（最近交易日 2026-10-16）。完整数字、分子分母与检验结果见 [docs/评测报告.md](docs/评测报告.md)（由 `npm run eval` 生成，带数据包哈希）；网页上每个指标都能点开看到具体回答。

| 指标 | V1 | V2 | V3（线上） | V4 换模型 | V5 亲和力 Prompt |
|---|---|---|---|---|---|
| 整体合格率 | 0/32 | 0/32 | 19/32 | 27/32 | 25/32 |
| 时效合格率 | 9/29 | 1/27 | 26/26 | 27/27 | 28/28 |
| 隐私复述 | 10/32 | 0/32 | 0/32 | 0/32 | 0/32 |
| 上下文最小化 | 0/32 | 0/32 | 32/32 | 32/32 | 32/32 |
| 画像不变性（组） | 1/4 | 3/4 | 3/4 | 2/4 | 4/4 |
| 风险揭示覆盖 | 10/20 | 13/20 | 10/20 | 17/20 | 13/20 |
| 闸门 | — | 阻断 | 阻断 | **阻断** | **通过** |

几条结论（详细数字见评测报告）：

1. **Prompt 修不了数据问题**：V1→V2 只换 Prompt，隐私复述从 10 条降到 0，但时效合格率反而从 9/29 降到 1/27。原因是新 Prompt 要求标注数据时点，模型如实写出了“截至 10 月 9 日”，旧缓存问题因此暴露出来。V2→V3 修复数据层后，时效 26/26，整体合格率 0→19/32（McNemar p<0.001）。
2. **最强的模型也会对画像选择性省略风险提示**：V4 整体合格率比 V3 高 25 个百分点（p=0.039），但有 2 个问题组只对部分画像附了风险提示，触发硬性规则“画像不变性 = 100%”，被阻断。
3. **直觉与数据不一致时按数据**：V5 的 P3 是运营提出的“给出更有信心的结论、肯定用户持仓”，预期会引发迎合。实测 32 条里没有出现红线命中或画像不一致，闸门放行。但 P3 删掉了适当性与画像不变约束，32 条评测集可能覆盖不到这类风险。建议补一批针对迎合的红队样本再全量。

## 4. AI 的角色

| 位置 | 用的是什么 | 说明 |
|---|---|---|
| 被测对象 | DeepSeek（deepseek-flash / deepseek-v4-pro） | 投资 Agent：LLM 路由 → 按数据版本取数 → 生成回答；全程记录 trace |
| LLM 评审 | deepseek-flash + 版本化评审 Prompt J1 | 只评相关性与个性化贴合，**不评数字对错**；原始输出与耗时入库 |
| 确定性引擎 | 规则 + 数据核验（无 LLM） | 数字抽取、比对、合规、隐私、适当性、归因、统计检验，可在浏览器复现 |
| 开发 | Claude Code | 编码与调试；人工核验过的问题见 [AI 使用与验证记录](docs/AI使用与验证记录.md) |

设计原则：能用数据和规则确定判断的，不交给 LLM；LLM 的结论与规则冲突时送人工，不由 LLM 单方面拍板。

## 5. 数据使用

| 数据 | 来源 | 说明 |
|---|---|---|
| 行情、估值、K 线、财务报表与指标、基金资料/净值/收益、个股资讯、热股榜 | 扶摇（同花顺金融数据 API），71 次真实调用 | 每条事实保留 endpoint、参数、request_id、抓取时间；见 `data/facts/` |
| 基金最大回撤 | 由复权净值序列推算 | 扶摇回撤接口对 5 只基金返回全 0，判为“数据未就绪”，改为推算并标注口径 |
| 产品风险等级（R1–R5） | 构造的适当性主数据 | 演示用，非任何机构的真实评级 |
| KYC 画像（6 个）、评测问题（23 题 / 32 项） | 匿名构造 | 问题中的手机号、证件号为明显无效的构造值（证件号月份为 13） |
| 用户行为反馈 | 按公开假设模拟 | 只演示用法，不作为实证结论 |

仓库内的扶摇数据是复现评测所需的小规模快照（约 1100 个数值和 60 条资讯标题）；原始接口响应（`data/raw/`）不入库。如数据方要求，可以删除 `data/facts/` 与 `public/data/`，用自己的 Key 重新抓取。

## 6. 运行方式

```bash
npm install
npm test            # 29 项单元测试
npm run eval        # 用仓库内数据重算评测，生成 public/data/bundle.json 与 docs/评测报告.md
npm run dev         # 本地打开控制台
```

重新抓数和重新生成回答需要 Key（写在 `.env`，已加入 `.gitignore`；模板见 `.env.example`）：

```bash
npm run fetch:facts   # FUYAO_API_KEY：抓扶摇事实快照
npm run run:agent     # DEEPSEEK_API_KEY：生成 5 个版本的回答（可断点续跑）
npm run run:judge     # DEEPSEEK_API_KEY：LLM 评审
npm run check:secrets # 发布前扫描，发现 Key 形态字符串即失败
```

GitHub Actions（`.github/workflows/pages.yml`）在每次推送时从仓库数据重新跑测试和评测，再构建并发布到 Pages。

## 7. 已知边界

- **评测集小**：每个版本 32 项，多数维度差异的 p 值 > 0.05，不应当成确定结论；页面已标注。
- **数字抽取靠规则**：对“当日/近5日 | -0.70% / +1.79%”这类斜杠表头、“单日涨跌和近5日”这类混写仍可能识别错（当前 160 条回答里剩 5 处误判，见评测报告）。这类误判会进入人工复核，由复核员推翻。
- **同日价格类指标互认**：开盘、最高、最低、昨收任一吻合都算有出处，避免把“最高 282 元”误判为错，代价是不检查数字和标签是否对应。
- **指代消歧**：就近标的核不上时，会用回答里提到的其他标的再试；极少数情况下可能张冠李戴。
- **净利润同比按归母口径核验**；报告期以“累计口径”为准，单季由相邻累计值相减得到。
- **D1 旧缓存的基金区间收益沿用最新值**（只有净值是 T-5），属于模拟设计的简化。
- **合规规则是关键词 + 语境规则**：对“稳定与保本是两件事”这类真正模糊的表述仍会命中，由人工确认；规则不能覆盖新出现的违规说法，要靠复核和用户反馈回补。
- **用户行为反馈是模拟的**；人工复核记录只保存在浏览器本地，没有后端与权限体系。
- 评测时点为周末（最近交易日 2026-10-16），没有覆盖盘中实时行情的分钟级时效。

## 8. 未做事项

- iFinD MCP 未接入（只接了扶摇 REST），宏观、政策类事实无法核验。
- 没有线上埋点和真实用户反馈；没有复核员账号、权限、审计日志和多人一致性（Cohen's κ）统计。
- LLM 评审没有与人工标注做系统校准；评审 Prompt 本身的版本对比未做。
- 没有对 V5 补针对“迎合”的红队样本；V2→V3 的多因素变更没有拆成单因素实验。
- 数字抽取未用 LLM 做交叉校验；公告全文与回答的逐句事实一致性（NLI）未做。
- 没有定时任务持续回放线上流量，目前是批量离线评测。
